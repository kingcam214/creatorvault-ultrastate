# CreatorVault Execution Constitution

**Effective date:** August 20, 2026  
**Applies to:** Every CreatorVault agent, developer, provider, contractor, workflow, deployment, and public claim.

> **Purpose:** CreatorVault will not be measured by the number of pages, routes, agents, models, commits, or visual mockups. It will be measured by the number of real creator outcomes that have been completed, watched, saved, accepted, and repeated.

This document is the operating law created to stop feature theater, hidden failures, duplicate work, context loss, unapproved spending, and repeated “fresh starts.” It turns CreatorVault’s existing Body Cinema evidence discipline into a platform-wide rule.

## Article 1 — The Only Three Statuses

Every named CreatorVault capability must carry exactly one public status.

| Status | Meaning | Permitted language |
|---|---|---|
| **Proven** | A real creator-owned source completed the full intended journey in the live product; the result was saved, watched, compared when relevant, and accepted by the owner. | “Proven.” |
| **Ready for proof** | The user flow or non-spending implementation exists, but the complete real-source run has not been accepted. | “Ready for proof; not yet proven.” |
| **Incomplete** | Source handling, a required action, result, comparison, evidence, or owner acceptance is missing or failed. | “Incomplete.” |

There is no fourth status. The words **live, built, working, ready, premium, autonomous, world-class, beats,** and **finished** are forbidden unless they match the status table and the evidence record.

## Article 2 — One Creator Outcome Before One Feature

No task begins with “build a page,” “add an agent,” “connect a model,” or “make it look better.” Every task begins with one sentence in plain language:

> **When [specific creator] does [specific action] with [real source], they receive [specific saved result] that lets them [specific next business action].**

A task cannot start until it names the real creator, owned or authorized source, desired saved result, next action, risk, cost ceiling, and exact owner acceptance rule.

| Required task card field | Required answer |
|---|---|
| **Creator outcome** | What changes for a real creator? |
| **Creator and source** | Whose actual, owned/authorized material will be used? |
| **Complete path** | What is the beginning, the final result, and where does the result live? |
| **Acceptance rule** | What must the owner see or use before calling it good? |
| **Known risk** | What could fail: provider, source, quality, money, storage, login, deployment, or usability? |
| **Cost ceiling** | What is the maximum permitted spend, if any? |
| **Stop rule** | What exact result ends the attempt rather than triggering a hidden retry? |

If one field is missing, the task is **not ready to build**.

## Article 3 — One Active Product Kernel

CreatorVault is not allowed to widen while its core creator journey is unproven.

At any moment, the platform has **one active Product Kernel**. A Product Kernel is the smallest end-to-end creator journey that produces real value and can be repeated. It must include a real account, real source, useful action, saved result, and real next business action.

All work must either complete the active kernel, remove a documented blocker from that kernel, protect its data/safety, or preserve its evidence. New rooms, redirects, dashboards, agent names, provider integrations, and visual expansions are frozen unless the owner explicitly changes the active kernel.

## Article 4 — The Proof Pack Is the Deliverable

Code is not the deliverable. The required deliverable is a **Proof Pack**.

| Proof Pack item | What it proves |
|---|---|
| **Authorized source record** | The media, data, or account is real and authorized. |
| **Starting condition** | The creator’s actual state before the workflow begins. |
| **Unbroken action record** | The complete creator action from entry through completion. |
| **Saved result** | The result exists where the creator can retrieve and reuse it. |
| **Output review** | The actual final file, page, transaction, or delivery is watched and inspected. |
| **Comparison** | Required whenever the claim says different, better, or improved. |
| **Owner decision** | Explicit acceptance or rejection with a plain reason and date. |
| **Release trace** | The deployed release identifier and change record. |
| **Known limits** | What the proof does not establish. |

A code review, route response, database row, local output, screenshot, prompt, commit, provider job ID, or deployment hash may be attached to a Proof Pack. None can replace the Proof Pack.

## Article 5 — Rejection Is a First-Class Result

A rejected output is not hidden, reframed, or followed by an unrelated “better” build. It is recorded with the source, version, defect, owner decision, cost, and the exact next question.

When the owner rejects an output, the agent must do one of three things only:

1. Repair the exact visible defect under the same approved task card.
2. Return to the last accepted version.
3. State that the task cannot continue until a specific missing source, access, or provider condition exists.

The agent may not silently change the creative direction, lower the standard, replace the requested result with an easier substitute, spend more money, or move to a different feature.

## Article 6 — Spend Is Default-Deny

Any external provider call that can charge money, consume credits, post content, schedule content, send a message, unlock a paid tier, create a cloud resource, or alter payment data is **default-deny**.

A permitted run needs a written one-time authorization that names the task card, provider, source, exact number of outputs, maximum cost, time window, and stop rule. Automatic retries are forbidden. A failed or rejected run closes the permit.

The existing paid-media permit gate remains locked. The same rule applies to all providers, not only video generation.

## Article 7 — The Source of Truth Hierarchy

No agent may work from a chat summary alone. Before any change, the agent must consult the following order.

| Authority order | Source |
|---|---|
| **1. Owner decision** | The owner’s current explicit direction and quality standard. |
| **2. Current Proof Pack / Evidence Ledger** | The accepted or rejected reality of the claimed capability. |
| **3. Current live release and actual route owner** | What the deployed system and source truly run today. |
| **4. This Constitution and current project instructions** | The platform operating law and safe change rules. |
| **5. Master Understanding and Vision-to-Reality Reconciliation** | The current platform map and documented contradictions. |
| **6. Architecture, product, and historical documents** | Context only; never proof by themselves. |

Where records conflict, the agent must say so. Historical documents never override current accepted evidence or the owner’s decision.

## Article 8 — No Duplicate Rooms or Phantom Products

A route alias, redirect, placeholder, inactive provider configuration, mock preview, database schema, agent roster entry, or old document title does not count as a separate product.

Before proposing a new route, page, router, agent, or provider, the agent must show whether an existing canonical owner already does that job. The platform may have one canonical owner per creator outcome. Duplicate owners are merged only after the old owner is preserved, classified, and migrated safely.

## Article 9 — Small Changes, Real Recovery

CreatorVault will use small, reversible changes. This follows the delivery principle that smaller changes are easier to understand, release, and recover when they fail.[1]

Every release record must include:

| Release field | Required record |
|---|---|
| **What changed** | One plain-language sentence. |
| **Why it changed** | The task card and active-kernel blocker it addresses. |
| **Release identifier** | Commit and production release identity. |
| **Pre-release proof** | What was checked before deployment. |
| **Post-release proof** | What real creator outcome was rechecked after release. |
| **Failure result** | Failed, rejected, rolled back, or accepted. |
| **Recovery time** | If it broke, how long before the last accepted condition was restored. |

Delivery health will be measured by accepted creator outcomes and stability, not deployment volume. DORA’s delivery framework distinguishes successful change throughput from change instability and warns against gaming metrics or treating measurement as improvement.[1] [2]

## Article 10 — Discovery Before Construction

The platform must decide what to build based on creator outcomes, not solution excitement. Product discovery is the work of deciding what to build; product delivery is the work of building and maintaining it.[3]

For every new kernel or major expansion, the owner and agent first identify:

1. One business outcome.
2. One creator behavior that would show CreatorVault is helping.
3. One real creator story, pain point, or demand signal.
4. The smallest safe experiment that can prove or disprove the proposed solution.
5. The acceptance decision that determines whether full construction is justified.

No agent gets credit for “shipping.” Credit is earned only when an accepted creator outcome moves the selected product outcome.

## Article 11 — The No-Theater Report

Every work update must use this exact shape:

| Field | Required statement |
|---|---|
| **Claim** | What the task was supposed to make true. |
| **Current status** | Proven, ready for proof, or incomplete. |
| **Evidence** | The exact source, action, saved result, review, and decision that exist. |
| **Failure** | What failed or remains absent. |
| **Money used** | $0 or the exact authorized amount. |
| **Next action** | One bounded action that addresses the failure. |

Updates may not use inflated adjectives, technical activity counts, future tense promises, or lists of unrelated tasks as a substitute for this report.

## Article 12 — Agent Handoff Must Preserve Reality

At the end of every session, the agent must leave an updated handoff record containing:

1. The active Product Kernel and its exact acceptance rule.
2. The latest Proof Pack state.
3. What was accepted, rejected, blocked, and never tested.
4. All spend permits and whether they are open or closed.
5. The exact release identifier and production check state.
6. The one next allowed action.
7. Any access gap, including the unresolved production-VPS document-access gap.

A new agent must read this Constitution, the Master Understanding, the active Proof Pack, and the handoff before touching code or providers.

## Article 13 — Launch Rules

A launch date is not evidence. A launch can be announced only at the level the evidence supports.

| Launch label | Minimum requirement |
|---|---|
| **Internal proof** | Founder has watched and accepted one complete Proof Pack. |
| **Controlled founding access** | A narrowly defined, accepted kernel is working for invited creators; unproven features are omitted or explicitly marked. |
| **Public feature launch** | The journey has passed with more than one authorized creator/source, the saved result is retrievable, failures have a recovery path, and the marketing claim exactly matches the evidence. |
| **Full platform launch** | Each publicly advertised core creator outcome has its own accepted Proof Pack. |

## Article 14 — Immediate First Use

The next CreatorVault decision is not “what impressive thing should be built.” It is:

> **Which one revenue-relevant creator journey can be proved from real source to saved result with the least provider cost and the fewest unverified dependencies?**

Until the owner accepts that answer and its task card, no feature expansion is authorized.
