# CreatorVault — Master Understanding After the Restart

**Prepared:** August 20, 2026  
**Purpose:** This is the factual starting point for every future CreatorVault task. It separates the owner’s real platform vision from code inventory, route inventory, historical plans, and directly accepted product evidence.

> **The plain truth:** CreatorVault is not “nothing.” It is a serious founder-built platform with a large codebase, a real live deployment, real creator-owned media infrastructure, a meaningful product vision, a governed provider system, and documented attempts at difficult capabilities. But it is also **not a finished, unified Creator Operating System today**. The platform has accumulated more named rooms and architectures than it has end-to-end proven creator workflows. That difference—not lack of ambition—is the core problem.

## 1. What CreatorVault Is Supposed to Be

CreatorVault’s original promise is a creator-owned operating system. A creator should not have to piece together a social profile, creation tools, storage, distribution, audience access, and monetization across unrelated platforms. The intended core is clear:

| Core pillar | Intended creator outcome |
|---|---|
| **Create** | A creator uploads or captures original media, turns it into usable content, and owns the finished asset. |
| **Own** | The creator keeps control of media, identity, audience, access, and data inside CreatorVault. |
| **Distribute** | The creator can prepare content for the right audience and channel without losing the source asset or the history around it. |
| **Monetize** | The creator can sell access, subscriptions, services, products, or paid media with transparent economics. |
| **Grow** | The creator receives useful signals, education, and direct business support rather than random dashboards. |

The platform is meant to serve creators in the United States, the Dominican Republic, and Haiti, with English, Spanish, and Haitian Creole support. Its founder promise is creator economics: the published product law says creators keep **85%** and the platform keeps **15%**. That promise must be reconciled with the older Bible record, which also documents a conflicting `70% creator / 30% platform` system setting. No percentage should be marketed until the live payment calculation is directly verified.

CreatorVault also has two intended product modes: **General Creator** and **VaultX**. The two modes have different audience, safety, distribution, and design requirements. They share infrastructure but must not be treated as one undifferentiated product or one interchangeable creator audience.

## 2. The Architecture That Exists on Paper and in Code

The accessible records consistently describe a real application stack: React/Vite/TypeScript on the front end; Node, Express, tRPC, MySQL, and Drizzle on the back end; PM2 and Nginx on the production VPS; GitHub-driven production deployment; and a public production domain. The live release endpoint confirms a production service currently responds with a named commit and that governed media execution and social outbound automation are currently disabled.

The platform contains many pages, routes, services, schemas, designs, historical providers, test artifacts, and feature documents. This is real platform material. It is not imaginary.

However, the evidence does **not** establish that every page, route, router, named agent, or advertised system completes its creator promise. The current route review found many URLs are simple forwards to a smaller number of pages. A forwarding URL is not its own product. A React screen is not proof that its user action succeeds. A router, database table, or deployment is not acceptance evidence.

## 3. Why the Platform Keeps Feeling Like a Restart

The records show five repeating patterns.

| Repeating pattern | What it caused |
|---|---|
| **Vision was treated as current reality.** | Big architecture documents called the OS live or complete while listing activation blockers, missing work, and unverified outcomes in the same document. |
| **Names became products before workflows did.** | Many different tool names and navigation routes point to a smaller number of pages or incomplete flows. This makes the platform look wider than it is. |
| **Code or deployment was treated as proof.** | Past rules had to explicitly say that `curl`, PM2, screenshots, code, database records, or a generated asset are not proof of a creator outcome. |
| **Work moved to the next feature before the last one was accepted.** | Agents kept adding infrastructure, pages, providers, and “systems” around an unproven core instead of finishing one creator journey. |
| **The permanent memory split in multiple directions.** | The Bible, learning logs, architecture files, old read-only copy, route source, production records, and historical audit files disagree in places about router ownership, build entry points, deployment mechanics, counts, and current capability. |

The concrete result is the owner’s experience: a platform that can look impressive and navigate through many rooms but has too few proven actions a real creator can complete and use.

## 4. The Evidence Discipline Already Exists — It Was Not Applied Everywhere

Body Cinema’s Evidence Standard is the strongest existing model for how CreatorVault should operate. It says a capability is not complete until the founder can watch it operate on a real creator-owned source, compare the output, trace the decision, and make an acceptance decision.

That standard has only three allowed labels:

| Label | Meaning |
|---|---|
| **Proven** | Complete watchable source → workflow → output → comparison → decision evidence exists. |
| **Demonstrable but unproven** | The page or non-spending logic exists, but no accepted real-source result has been captured. |
| **Incomplete** | The needed source handling, result, comparison, or evidence is absent. |

This is the law the whole platform must adopt. It answers the owner’s question about how to stop AI theater: no agent is allowed to substitute an architecture, a route, an output file, a mock, or an explanation for the source-to-result proof record.

## 5. Current Reality of the Most Important Advanced Claims

### KingCam

The KingCam finish line is correctly documented: recognizable identity, full visible body, natural continuous motion, verified voice, believable mouth performance, and a real CreatorVault teaching or tool demonstration in the same watchable output.

That output does **not** exist today. Real source material exists. Real ElevenLabs voice material exists. Real provider attempts and hard lessons exist. The owned pipeline and Canon concept exist. But no accepted full-body talking KingCam video has passed the stated finish line. Previous partial outputs are building blocks only and must not be publicly sold as the finished clone.

### Body Cinema

Body Cinema has source analysis concepts, treatment plans, packaged motion previews, no-spend review logic, and a strict evidence ledger. Its ledger is honest: previews are proven as packaged files but not as a live creator experience; real-source analysis is demonstrable but unproven; four materially distinct creator outputs are incomplete; paid drops, competitor superiority, and revenue lift are incomplete.

### Marketing Maker / KillaGraphics

The KillaGraphics design DNA and the owner’s historical work are real. The current automated proof was rejected by the owner because it did not blend into the owner’s standard: people floated instead of belonging to the art, typography was generic, and the output looked below the professional bar. That is a failed creative proof, not a foundation for a launch claim.

### Social, Automation, and Revenue

The current production release record says outbound social automation is disabled. The provider catalog is visible, but source-video generation lanes are not enabled for execution. Payment, subscription, payout, and outreach surfaces cannot be treated as business-ready until the exact real payment, creator record, and delivery outcomes are re-watched and accepted.

## 6. The Source-of-Truth Conflict That Must Be Fixed

Multiple records cannot all be current at once. Examples include:

| Conflict | Restart rule |
|---|---|
| One legacy record says `server/routers.ts` is the only canonical registry; the current learning log says both `server/_core/routers.ts` and `server/routers.ts` must be updated. | The actual production entry point and currently deployed source must be checked before any router change. No document wins over current verified source and runtime. |
| Old records describe direct SSH access and a different deploy/sync model; current project guidance describes a self-hosted GitHub Actions production runner. | The current deployment workflow and release metadata are the operational truth until direct production records prove otherwise. |
| Architecture files make broad “live” claims while evidence files list blocked dependencies or no accepted creator output. | A claim is governed by its current evidence ledger, never by the architecture’s language. |
| The Bible lists a huge route and router world; the current route source shows many redirects to a much smaller surface. | A redirect is navigation only. It is never a separate tool count. |
| Creator earnings are documented as both 85/15 and 70/30. | No monetization percentage can be promoted until the live transaction and payout calculation are verified. |

## 7. What Must Be Preserved

Starting over does **not** mean throwing away the platform or wiping code. The following are valuable and must be preserved:

1. The founder’s core Creator Operating System vision and creator-ownership principles.
2. Creator-owned media and permanent source/evidence records.
3. The current live deployment, database, source code, Git history, and production release trace.
4. The existing evidence laws, especially Body Cinema’s source-to-output acceptance standard.
5. KingCam’s real source material, verified voice assets, rejection history, and provider cost safeguards.
6. The owner’s KillaGraphics design DNA and client-standard quality bar.
7. The payment and safety routes, which must not be touched casually because they can affect real people and money.

## 8. What Must Stop Immediately

1. Launching new named rooms, redirects, agents, or dashboards before the last creator workflow is accepted.
2. Saying “live,” “working,” “complete,” “world-class,” “Canva-beating,” “autonomous,” or “proven” without the required evidence record.
3. Spending provider credits as a substitute for a clear source, acceptance rule, and fixed stop condition.
4. Replacing functioning code or performing broad rewrites to make a page look new.
5. Carrying old plans, old audit statements, and old screenshots forward as if they prove the live platform today.
6. Letting a new agent work from a conversational summary instead of this master understanding, the current evidence ledger, the actual route owner, and the production release record.

## 9. The Restart Is Not Another Feature Build

The restart is a product recovery operation.

The first outcome is a single **Canonical Product Kernel**: one narrowly defined creator journey that moves from a real account to a real saved outcome and then to a real next business action. It will be selected only after the launch/reality reconciliation phase identifies the simplest money-relevant journey with the fewest unproven dependencies.

Until that journey has a source, a user action, a saved output, a review recording, an owner decision, and a way to find the result later, CreatorVault is not allowed to widen again.

## 10. Evidence Coverage and Open Gaps

This synthesis is based on the full local document catalog, accessible primary records, live release metadata, current route-source review, connected caption-worker records, and completed wide research. The catalog contains 273 serious accessible local records. Two wide-research document families did not complete because their isolated research environment could not mount the original source paths; those incomplete outputs are not treated as content evidence.

The production VPS document root remains an explicit open gap. The recorded password was rejected, and the documented passwordless key/alias is not available in either connected environment. Therefore this document does **not** claim complete mastery of files that exist only on `/root/creatorvault`, including runtime logs, live secrets, uploads, and direct production-side records. That access issue must be resolved internally without asking the owner to perform technical work.
